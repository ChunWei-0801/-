# 家庭記帳：發表與驗收手冊

這份手冊把「產品展示」「程式驗收」「模型研究」分開記錄。展示資料是虛構範例；預期金額可人工驗算。測試通過數、模型指標與線上部署結果，只能填實際執行的結果。

投影簡報：[`frontend/docs/presentation.html`](../frontend/docs/presentation.html)；操作教學：[`frontend/docs/tutorial.html`](../frontend/docs/tutorial.html)；英中名詞：[`frontend/docs/glossary.html`](../frontend/docs/glossary.html)。三頁使用本機資產，不需要 CDN。

## 1. 發表前要確定的事

- 用 `python run.py --sqlite` 可走免 Docker 的完整本機流程；`python run.py` 保留 PostgreSQL 工作流程。以啟動時印出的 URL 為準。
- 瀏覽器連接真 API，預設為 `http://localhost:5174/?api=http://localhost:8000`。`--front-only` 的 mock 只適合介面練習，不能作為後端驗收證據。
- 沒有 `MODEL_BASE_URL` 時，模型解析路由回 503，前端以規則備援；確認寫入仍呼叫真 API。規則不是微調模型，必須說明當下模式。
- **模型訓練未執行；正式人工留出集評測未執行。** 不宣稱已取得 LoRA 權重、準確率、Macro-F1、低延遲或超越其他模型。
- Render 設定是部署方案；沒有實際建立並驗證服務，就不能說已公開上線。自己的部署流程見 [05-部署指南.md](05-部署指南.md)。

簡報按 `←`／`→` 或 PageUp／PageDown 切頁，Home／End 跳首尾，`N` 顯示講者備註。可列印成 PDF。停用 JavaScript 時，所有投影片仍依序可讀。

## 2. 5–8 分鐘講稿

以下約 6 分 30 秒，留最多 1 分 30 秒給問題。若課程限制五分鐘，縮短架構與評測各20秒，實機只記一批資料並展示一個反向權限案例。

| 時間 | 畫面 | 講稿與動作 |
|---|---|---|
| 0:00–0:25 | 簡報1 | 「我們想讓每天記帳少一點填表負擔，讓家庭在清楚的權限界線內看懂收支。」一句話定位：段落記帳、月年控管、唯讀監管。 |
| 0:25–0:55 | 簡報2–3 | 「一句話可能有多筆交易，也可能沒有講金額。我們先解析、讓人確認，最後才寫入。」點出咖啡沒有金額，不能靠常識填60。 |
| 0:55–1:30 | 簡報4 | 「前端是靜態網頁；FastAPI驗證身分、權限和金額；資料庫保存紀錄。LLM處理語言，不直接寫入、不算錢。」說明展示SQLite與正式PostgreSQL差別。 |
| 1:30–4:00 | 實機 | A/B兩個獨立視窗。展示角色，A貼段落、檢查模式、咖啡補65、確認寫入。重新整理，查看收入1500、支出120、結餘1380。餐飲預算100，展示超支20。 |
| 4:00–4:45 | 實機／簡報6 | 「能看到不等於能代改。」B子女不能取得全家資料；直接查A的個人明細也被拒絕。A獲監管權後能讀B，不能替B改帳。 |
| 4:45–5:20 | 簡報7 | 「若目前是規則備援，這是可用性展示，不是模型成效。我們提供模型串接位置，沒有在這次執行微調。」說明few-shot和微調的差別。 |
| 5:20–6:00 | 簡報8–9 | 「用同一人工留出集比較規則、零樣本、few-shot與微調，量整段完全正確率、Macro-F1、缺值亂猜與延遲。尚未跑的數字保留未測。」程式測試結果只引用本手冊已填的紀錄。 |
| 6:00–6:30 | 簡報12 | 「接下來先標註與建立基準線，再由實測決定是否微調。產品保留人的確認權與家庭資料界線。」結尾邀請問題。 |

用「我有測到什麼」回答，避免「應該全部可用」「模型非常準」這種沒有證據的句子。

## 3. 兩帳號展示腳本

### 彩排準備

1. 啟動完整前後端，確認 `/readyz` 可回應。開發服務綁定與埠號以終端機為準。
2. A使用一般視窗，B使用無痕視窗或另一個瀏覽器。一般視窗的兩個分頁通常共享登入儲存，不能模擬兩人。
3. 自建新的展示帳號：A「家長示範」、B「子女示範」，不同 email、各自設定密碼，完成個人化設定。不要投影密碼或token。
4. A建立「展示家庭」，產生角色為child的邀請碼，必填label如「展示子女」。B輸入碼加入。
5. 兩人使用空帳、相同月份與預設總帳範圍。記下原有交易數；若有舊資料，另建展示帳號，不在台上重設資料庫。
6. 若展示監管，A先建立對B的監管關係，確認B的資料範圍與唯讀限制。家長角色不等於自動獲得每個子女的完整明細。

### 實機順序與預期

| 操作 | 預期效果 | 證據 |
|---|---|---|
| A/B分別登入 | 顯示不同帳號與parent／child角色 | 畫面身分、`GET /api/auth/me` |
| A貼「今天早餐55，今天在全家買咖啡，今天打工賺了1500。」 | 解析預覽可檢查與修正；咖啡金額不應被憑空補入 | Network解析回應、模式標示 |
| 人工檢查切分、日期、收支與分類 | 目標結果為三筆：支出55、支出65、收入1500 | 三筆預覽，咖啡65為人補的示例金額 |
| 按確認 | 三筆新增到後端 | confirm-batch成功、交易列表 |
| 重新整理、讀同帳號 | 明細仍存在 | `GET /api/transactions`和另一個瀏覽器讀取 |
| A看個人本月統計 | 收入1500、支出120、結餘1380 | 明細對照summary；僅在空帳與正確範圍成立 |
| A設餐飲預算100 | used120，超支20，使用率120% | 預算畫面和API |
| B手動記交通80 | B個人支出80 | B自己的明細 |
| A查允許的家庭範圍 | 全家收入1500、支出200、結餘1300 | 合法範圍summary；先確認監管與權限 |
| B嘗試全家summary | 接口只回自己的合法範圍，不提供家人的完整資料 | HTTP200也必須檢查內容，不以狀態碼判斷有無越權 |
| B直接查A的個人明細 | 不回A的私人交易 | `GET /api/transactions?userId=A的id` 回403 |
| A嘗試改B的交易 | 即使可以讀，仍拒絕代改 | 403／404，B原交易不變 |

**注意：**這是人工確認後的教學期望，不是對所有解析器的「必定正確」承諾。切分錯誤是失敗案例，現場應如實修正或轉手動流程。

## 4. 驗收清單

下方勾選項供每次正式發表前重跑；本次已測結果見「驗收紀錄」與 [VALIDATION](VALIDATION.md)。

### 必要功能與邊界

- [ ] 真API註冊、登入、登出與個人資料，沒有mock代替。
- [ ] 解析不寫入；確認後才新增交易；重新整理／另一個瀏覽器仍能讀。
- [ ] 空白、超長文字、缺金額、非法日期與不符合收支的分類有明確結果。
- [ ] 金額0、負數、小數與大值依契約驗證，沒有崩潰或字串拼接加總。
- [ ] 批次其中一筆非法時，所有筆都不寫入；核對交易數與解析紀錄，不只看HTTP狀態。
- [ ] 個人與家庭的月年統計、分類統計與篩選能由明細人工驗算。
- [ ] 預算、存款目標、提醒與通知，依設定正確產生或不產生。
- [ ] 家庭邀請、加入、角色、監管與解除，確認資料範圍會更新。
- [ ] 登入錯誤不暴露帳號是否存在；登出後舊token依規格不能繼續使用。
- [ ] 年度不足資料不被誤導為完整年度；存款目標不當成銀行餘額。

### 反向權限

- [ ] 未登入不能讀交易、家庭與統計。
- [ ] 子女改URL或直接API也不能查全家。
- [ ] 不能讀無關家庭、無監管／共用帳本關係的人。
- [ ] 不能改、刪或確認寫入為別人的個人交易。
- [ ] 平台管理員不因管理身分獲得全家財務資料。
- [ ] 不存在登入他人帳號的`/api/auth/switch`。

### AI與外部整合

- [ ] 未設定模型／模型逾時時明確顯示規則備援。
- [ ] 501、後端斷線、未授權拒絕不能被備援掩蓋。
- [ ] `model_ver`或來源能分辨rules與模型；規則樣本不能當模型正確率。
- [ ] 真模型實測與模擬client測試分開記錄。
- [ ] 若展示忘記密碼，Brevo與寄件人已設定，真的收到並使用重設連結；否則明列未驗證。
- [ ] 若宣稱部署完成，已在自己的公開網址走完整真API流程，不只檢查Render顯示Live。

## 6. 常見答辯

**Q：為什麼還需要LLM，規則不是也能解析？**  
A：規則可處理固定金額與字詞，是必要基準線。複雜語意與切分可能需要模型，但優勢必須用同一人工留出集證明。這次沒有正式比較結果，不宣稱模型一定勝出。

**Q：目前算不算AI專題成果完成？**  
A：產品與模型是兩條驗收線。可以展示可用流程和模型串接設計；訓練未執行、留出集未測，就明確列為未完成的模型工作，不以規則假裝微調成果。

**Q：Few-shot是不是微調？**  
A：不是。Few-shot在提示內容放例子，不更新權重；微調會用資料更新模型或adapter參數。

**Q：咖啡金額沒講，模型可以估計嗎？**  
A：記帳不能把常識估價當真實交易。缺值應留空，由使用者補齐，再確認寫入。

**Q：你們報告的1380是哪來的？**  
A：教學中收入1500、支出55+65，共120，所以結餘1380。它是交易數字，不是準確率；實際總計由後端在正確範圍加總。

**Q：家長是否可以改孩子的帳？**  
A：監管關係提供閱讀權限，不提供代改身分。以反向API測試確認拒絕，紀錄應保留原操作者。

**Q：藏按鈕就安全嗎？**  
A：不夠。瀏覽器請求可以自己組，必須由後端對每支路由檢查身分、範圍與資料所有權。

**Q：SQLite與PostgreSQL測試都一樣嗎？**  
A：有差異。SQLite適合快速與本機展示，正式PG要另外驗證型別、約束與交易。沒有跑PG就不能用SQLite結果代稱已測PG。

**Q：回200或所有unit tests通過，能證明模型很準嗎？**  
A：只能證明測到的程式行為。模型需要人工留出集、固定版本與客觀比較；模擬模型回應的測試不算真模型評測。

**Q：下一步先做什麼？**  
A：人工標註與難例基準、真實服務延遲、錯誤分析，再決定few-shot或微調。先確定改進有證據，再推進正式部署與多人使用。

## 8. AI評測與訓練：尚待執行的步驟

完整原始規劃見 [03-LLM實作規劃.md](03-LLM實作規劃.md)。原規劃中的資料數量、目標與指令是計畫，不是已完成的成果。執行前確認相應工具真的存在，避免直接複製尚未實作的命令。

1. **定標註規則。** 固定分類清單、收支、span（原句片段）、缺值與參考日期。「沒寫金額」標null，不猜；模糊樣本由兩人覆核。紀錄資料來源、必要同意與去識別化。
2. **人工資料分割。** 建立訓練、驗證、人工留出測試三份資料；相同或近似模板按群組分割，避免換店名或金额形成洩漏。留出集不送商業LLM標註，不用来调prompt。
3. **固定推論条件。** 同一分類、參考日期、輸出schema、後處理、模型版本、temperature與服務。記錄模型名稱／revision、prompt hash、程式版本與資料集hash。
4. **先跑基準。** 規則、zero-shot、few-shot各跑同一人工留出集，保留每段原文、gold、prediction、模式與錯誤。外部模型失敗與fallback单独计數，不能把规则回應算模型正确。
5. **算清楚指標。** 格式合法率；筆數與配對正確率；整段各交易的日期／金額／收支／分類完全正確率；固定分類集合的Macro-F1；缺金額亂猜率；p50/p95延遲。每個比率都附分母、失敗样本处理規則與資料集版本。
6. **評財務建議。** 用固定已算數字檢查看是否編出新數字／不支持的結論；匿名、打亂版本順序做盲評。提供評分規則與評者人數，不能把主觀「好用」換成抽取準確率。
