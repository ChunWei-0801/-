# 教師回饋補強：展示與驗證指南

本指南配合 v187 專題補強。功能是否已發布應以最新部署紀錄為準；本文件與自動化測試不能替代正式網站、實體手機或真實模型的驗收。

## 展示入口

- `/demo.html`：不需要正式帳號的專題試用，使用獨立的瀏覽器示範資料。
- `/index.html#/financial-planning`：登入後的理財規劃，使用目前帳號有權限讀取的帳務。外部匯率需實際成功取回，才能列為該次 API 串接成功。
- `/index.html#/allowance-simulation`：登入後的親子零用錢模擬；若尚無合法監管關係，需先依家庭功能建立關係。
- `/rag-evaluation.html`：24 題固定虛構情境的本機 RAG 對照評估。
- `/receipt-lab.html`：圖片 OCR、來源規則、品項總額與人工確認的研究流程。

路徑須加上實際部署網址，不能以 GitHub 的原始碼網址當作可操作網站。

## 一、讓同學實際試用

示範頁以家長、孩子、朋友等示範身分及虛構收支資料提供操作。這些是試用身分，不是已註冊的正式帳號，也不會寄送驗證信。資料與正式權杖、帳務分開，依目前瀏覽器保存；不同裝置不會自動共享同一份示範資料。

建議發放以下任務：新增一筆記帳、修改金額、依月份找報表並匯出、試用活動邀請、安排儲蓄及模擬發放零用錢。記錄是否完成、花費時間與遇到的問題。匿名體驗紀錄不含帳務全文，不能把瀏覽器內完成任務的次數直接當作真實使用者人數。

同學可自由重設自己的示範資料，重設不應影響正式網站。需要真人註冊、家庭邀請或跨裝置同步的測試，則使用各自的正式測試帳號與虛構內容，另行記錄結果；不可把本機角色切換當成多人線上同步已驗收。

## 二、展示 RAG 如何協助理財規劃

建議情境：「四個月後帶孩子去日本，預計花費 30 萬日圓，期間也要保留孩子零用錢，可以怎麼安排？」

1. 確認目標幣別、已存台幣、期限與可持續投入金額。帳務不完整時，讓使用者補入明確標示的假設。
2. 取得目前帳號可見的收支證據；不得以自然語言放寬家庭或監管權限。
3. 外幣目標實際呼叫匯率服務，顯示來源、更新時間及過期狀態。參考匯率不等於銀行成交價，不含保證可取得的換匯成本。
4. BM25 檢索與問題相關的理財教育摘要，展示來源連結、摘要檢視日與原文日期資訊。
5. 程式使用 Decimal 試算資金缺口、每月所需與可行性。模型只根據供給的事實與摘要解釋方案；不能把模型生成的數字當作正式計算結果。 投入日期只計入今天起每滿一個月且不晚於截止日的日期；最後不足一個月不另增加整月投入能力。若截止日不足一個完整月，畫面只展示一次性需備妥金額，必須另外確認即時資金，不能用每月結餘宣稱已可達成。
6. 由使用者比較方案，再明確確認是否建立目標。沒有模型時仍可看程式試算；不能將規則文字標成已完成的模型回答。

財經知識庫是自行撰寫的教育摘要與參考連結，不是已取得整本理財書籍的授權，也不是對整個網路即時搜尋。政府防詐 CSV 屬開放資料匯入，應與外部 API 呼叫分開說明。

## 三、做同一題有／無 RAG 的實驗

評估工作台的題庫有 24 題，分為家庭旅行、資金不足、資料未知與已達目標四種虛構情境。每題兩個模式使用相同問題、同一模型設定與相同虛構事實：

- 「沒有理財知識檢索」：只有共同的虛構財務事實；並非完全沒有證據。
- 「有 RAG 理財知識檢索」：另外加入 BM25 實際檢索到的至多三則教育摘要。

操作順序：

1. 先查看共同事實及人工核對標準；標準不會送進模型。
2. 確認下載選項，再啟動約 290 MB 的本機 Qwen 0.5B 模型。需要支援 WebGPU；不支援或載入失敗時，列為未測，不能補造結果。
3. 手動執行其中一種模式，等待完成或取消，再執行另一種。頁面不會自動跑完整題庫。
4. 對照實際提供的來源，分別評定「內容及數字正確」「引用支持回答」。預設都是未評分；格式正確的引用不能證明內容正確。
5. 下載匿名評估 JSON。紀錄含題目 ID、模式、模型、來源 ID、實測時間、Token、失敗碼與人工評分；不含回答全文、私人帳務或圖片。

建議在相同裝置交替兩種模式的先後順序，分開記錄首次下載／載入及已載入後推論時間。若需要較穩健的成效分析，應使用預先訂好的評分標準、多人獨立核對及重複測試；本頁不自動產生「提升多少準確率」的結論。檢索無命中的題目，也不能算成有命中來源的 RAG 成效。

## 四、親子零用錢模擬

家長選擇有權限的孩子，輸入金額並確認，雙方能查看同一筆模擬紀錄。重送同一次操作不應重複發放；陌生人不得查看紀錄。

此功能不會向銀行扣款，不是支付工具，不代表真實資金已轉入孩子帳戶，也不應混入真實收入與支出。真正轉帳要依銀行或支付業者的合作、授權與驗證流程另行規劃。

可展示的教育價值為：討論零用錢用途、約定與規劃、記錄發放、觀察習慣；不把「有一個轉帳按鈕」當作已完成銀行 API 整合。

## 五、圖片記帳與多模態展望

圖片研究室可選擇真實圖檔在本機 OCR，或先使用明確標示的示範文字。核對原文、日期、幣別、總額與品項，發現差額時補正或明確確認，再下載人工核對的草稿。研究室不會寫入正式帳務。

目前是「圖片 → OCR 文字 → 來源規則 → 人工確認」，尚未整合視覺語言模型。未來可以研究以開源視覺模型同時理解版面與文字、分辨品項和折扣、核對付款截圖；需評估授權、裝置能力與真實辨識品質。詳見 [多模態路線](MULTIMODAL-ROADMAP.md)。

## 報告應清楚分開的證據

| 項目 | 可以記錄的證據 | 不能直接推論 |
| --- | --- | --- |
| 自動化測試 | 權限、數值、取消、介面與契約通過 | 真實模型準確率、實體手機操作都通過 |
| RAG 檢索 | 題目實際命中的摘要與來源 | 模型一定讀懂或正確引用 |
| 模型實測 | 裝置上完成狀態、時間、Token、人工評分 | 未測裝置也有同樣速度或普遍穩定性 |
| 外部 API | 該次成功取回資料、來源及更新時間 | 所有 API 永遠免費、匯率為即時成交價 |
| 零用錢模擬 | 合法角色看同一筆紀錄、防重送 | 已完成銀行匯款 |
| 收據 OCR | 真實照片的原文、草稿與人工標準答案 | 已完成視覺 LLM、多模態模型辨識 |

現階段仍須補充的實機證據包括：真實 WebGPU 裝置的兩模式對照、iPhone／Android 實際相機與觸控、真實收據辨識、正式帳號跨裝置與邀請，以及正式環境的匯率 API 完整流程。尚未測量的項目維持待驗證。
