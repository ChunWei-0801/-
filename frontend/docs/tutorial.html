先分清楚：規則解析是 Rules；模型推論是 LLM；微調是 Fine-tuning。現在沒有產出或驗證微調權重。未設定模型時，解析 API 回 503，前端使用規則備援；確認後的交易仍寫入真實後端資料庫。API 連不上或尚未實作，不能當成模型備援。

啟動完整前後端Start the frontend and backend

在專案根目錄，也就是 run.py 所在的資料夾執行。每個雲端任務已有隔離環境，直接使用現有 checkout，不需要另外建立 Git worktree。

python run.py --sqlite

預期效果：安裝必要套件、初始化本機 SQLite 資料庫與預設分類，啟動前端與 API。以終端機印出的網址為準，預設如下：

用途預設網址怎麼確認
前端連真 APIhttp://localhost:5174/?api=http://localhost:8000看到登入頁，API 狀態指向本機後端
健康檢查http://localhost:8000/healthz回應 HTTP 200；此檢查不代表所有功能已驗收
互動 API 文件http://localhost:8000/docs能閱讀路由、請求格式與回應 schema

要使用 PostgreSQL，先啟動 Docker，再執行 python run.py。兩種模式都是後端持久化資料；SQLite 與 PostgreSQL 是不同資料庫，不會自動搬移彼此的資料。python run.py --front-only 只適合前端 mock 操作練習，不能證明 API 或資料庫已串接。

操作本系統請用 HTTP 網址，不要直接開 file://.../index.html。本頁教學、名詞表與簡報本身可以離線讀取。

想手動了解初始化的每一步？

先讀 backend/.env.example 與 backend/README.md。一般流程依序是安裝 backend/requirements.txt、設定資料庫與 JWT、alembic upgrade head、python -m app.cli init-db，再執行 uvicorn app.main:app。請在 backend/ 執行後端命令；展示時用一鍵啟動比較不容易漏步驟。

準備兩個帳號與一個家庭Accounts, family roles and separate sessions

  1. 用一般瀏覽器視窗註冊 A：名字「家長示範」、你可管理的展示用 email，以及自己設定的密碼。走完個人化設定。
  2. 開啟「家庭成員」#/members，建立「展示家庭」。建立者為家庭家長。
  3. 產生子女角色的邀請碼，複製到自己的展示筆記。這是加入家庭的邀請，不是登入別人的權杖。
  4. 開啟無痕視窗或另一個瀏覽器，註冊 B：「子女示範」，用不同 email。走完個人化設定後，輸入邀請碼加入家庭。
  5. 分別重新整理兩個視窗，確認 A、B 顯示不同使用者，同一個家庭，且角色正確。

預期效果：A 和 B 有各自的登入工作階段，A 的家庭列表看到兩人。一般視窗的兩個分頁通常共享瀏覽器儲存，所以不能當成兩個獨立帳號。

不要把真正的家人資料拿來投影。用新的展示帳號、空帳與虛構消費即可；重複彩排時換帳號或記下原本資料，避免把累積總額誤認為這次示例。

解析一段話，補缺值，再確認Parse → Review → Confirm

A 進入「收支明細」#/entry，展開「記一筆」，選擇「段落記帳」。貼上：

今天早餐55，今天在全家買咖啡，今天打工賺了1500。
  1. 按「解析這段話」，先看目前是模型解析還是規則備援。
  2. 對照原文檢查筆數、日期、收支與分類。解析可能出錯，下面是人工確認後想得到的示意，不是保證每個模型都會輸出一樣的結果。
  3. 咖啡沒寫金額，應留空。填入教學金額 65；如果日期、分類或切分有誤，一併修正。
  4. 確認早餐／咖啡是支出、打工是收入，三筆都完整後，按「確認並寫入」。
必填或低信心：需要檢查預覽：尚未寫入確認成功：後端已接受

預期效果：明細中出現確認後的三筆。重新整理仍存在，登入同帳號的另一個瀏覽器也能讀取。若畫面說「寫入失敗」，保留原輸入，排除錯誤後再確認，不要把預覽當成已入帳。

想完全手動記帳？切到「單筆手動」，自己填日期、金額、收支、分類與備註。這條流程不需要模型服務。

驗算統計，設定第一個預算Summary, budget and savings goal

在 A 的空帳、同一月份、沒有其他交易且只看「我」時，回總覽 #/ 或「統計」#/stats：

Income · 收入

1,500

打工收入

Expense · 支出

120

55 + 65

Net · 結餘

1,380

1,500 − 120

  1. 確認月份、範圍與帳本篩選沒有排除這三筆。
  2. 把本月餐飲預算設成 100。餐飲用了120，示例使用率120%，超出20。
  3. 可再設定每月存款目標；比較目標與結餘。存款目標是使用者的規劃，不能當成銀行實際存款。
  4. 切到年度統計；如果只有少數月份有資料，應說明這是目前已記錄資料，不能稱為完整年度財務。
  5. B 在自己的帳上手動記一筆「交通支出80」。A 查看獲授權的家庭範圍：在上述空帳假設下，全家支出200、收入1500、結餘1300。

先看明細，再看總計。金額由後端依目前可見範圍加總。數字對不上時先檢查月份、帳本、資料重複與角色，不要要求模型替你重算。

驗證「看得到」與「不能代改」Authorization and negative tests

家庭家長與監管者是不同概念。若要讓 A 查看 B 的個人明細，依介面建立適當監管關係，再開啟唯讀監管檢視。使用 A 的帳號查看，不要登入 B 的帳號。

驗證情境操作預期效果
B 為子女檢查「全家」切換是否可用不能取得全家統計
B 直接呼叫 API用 B 自己的權杖呼叫 GET /api/summary?scope=family只能取得自己的合法範圍，不能回傳其他家人的數字；此接口可能回200
A 已獲監管權查 B 個人明細，再嘗試更新 B 的交易讀取允許；更新拒絕
B 直接查 A 的個人帳呼叫 GET /api/transactions?userId=A的id403；不得回 A 的私人明細
未登入不帶權杖呼叫交易 API401，不能取得私人資料
另一個家庭用沒有關係的帳號查 B 資料403或404；不得回私人交易內容
API 測試怎麼操作？

在本機 API 文件 http://localhost:8000/docs，先執行登入取得自己的 accessToken。若頁面提供 Authorize，填入自己的 token，再測目標路由。若版本未提供授權按鈕，用開發者工具 Network 找到自己的請求，複製成 fetch，僅更改目標路由或參數。權杖只放在自己電腦的測試工具，投影和截圖不要顯示它。

// 僅在自己瀏覽器的開發者工具練習；請先填自己的 B 權杖。
// 這段示意不會自動執行。
fetch('http://localhost:8000/api/summary?scope=family', {
  headers: { Authorization: 'Bearer <B自己的accessToken>' }
}).then(async response => ({
  status: response.status,
  body: await response.json()
})).then(console.log)

不只檢查畫面有沒有按鈕。後端拒絕非法請求，才支持「權限有效」這個說法。測試結果與具體狀態碼寫入發表驗收手冊。

從畫面追到資料庫：實作路線Trace a request end to end

  1. 先讀契約。docs/02-前後端串接契約.md 定義前端收什麼；舊文件的 stub 與時程敘述是原始規劃，現況以程式與測試為準。
  2. 看畫面。從 frontend/js/app.js 的段落解析按鈕追到 API.nlpParseBatch，再看 api.js 的 HTTP 轉接器。
  3. 看入口。backend/app/routers/ledger/nlp.py 區分 parse（不寫入）與 confirm（驗證後寫入）。Pydantic schemas 限制請求格式。
  4. 看規則。服務層負責解析、統計；guards 決定可見與可改範圍。資料模型與 Alembic 負責表結構。
  5. 先做局部驗證，再整體跑。不要看到「回200」就結束，還要看資料型別、正確數字、拒絕未授權請求及回滾效果。
cd backend
python -m app.ownership
python -m pytest tests/routes
python -m pytest

預期效果：分工檢查與測試產生實際結果。被跳過（skipped）不算已通過的功能；使用 stub 的參考測試也不能替代真實實作驗收。模型模擬測試不等於已測過外部模型。

常見英文中文意思這裡的例子
Request / Response請求／回應送文字給 parse-batch，拿回 items
Schema / Validation資料結構／驗證日期格式、amount型別、必要欄位
Transaction / Rollback資料庫交易／回滾批次其中一筆非法時全部不寫
Scope / Permission資料範圍／權限me、family和監管可見對象

設定模型，保持結果可追溯Model integration and honest evaluation

先有可用的模型 HTTP 服務，再在本機 backend/.env 或正式平台的環境設定填入必要變數。不要把金鑰提交到 Git，也不要貼在聊天中。

名稱用途注意
MODEL_BASE_URL模型服務 base URL服務須支援目前 client 使用的 OpenAI 相容 chat completions
MODEL_NAME服務接受的模型識別名稱與服務所提供的名稱一致，並記錄版本
MODEL_API_KEY模型服務授權若服務需要才設定；存在安全環境欄位
MODEL_TIMEOUT_SECONDS呼叫逾時測量延遲後再調整；不要用無限等待掩蓋問題
  1. 重新啟動後端，先確認模型服務的健康與回應格式，再從系統解析同一段文字。
  2. 觀察模式標示與 Network 回應。如果顯示 fallback／規則，這筆就不能算模型成功案例。
  3. 保留原始輸入、解析、使用者修正與版本。使用者修正是候選標註，須人工整理後才能進訓練集。
  4. 規劃 QLoRA 前先做人工訓練／驗證／留出資料分割，固定分類、參考日期與評測腳本。完整步驟見 docs/04-發表與驗收手冊.md。

目前模型訓練未執行、正式模型評測未執行。訓練規劃不等於訓練成果；不要把教學示例、單元測試或自己看過的句子當成留出集準確率。

遇到問題，先確認哪一層Troubleshooting

現象先查下一步
連不上後端/healthz、終端機服務是否仍在、網址與埠號確認 API 已啟動；查看CORS允許來源是否等於前端實際來源
401／403目前帳號、登入狀態、家庭角色、資料範圍用正確帳號與自己權杖重試；不移除後端權限檢查
422回應 detail、Network 的請求內容修正欄位型別、日期格式與必填值
解析503模型服務是否設定／健康可用規則或手動記帳；清楚說明模式，資料寫入仍走後端
501是哪一支路由、是否仍是stub這是功能未完成，不能宣稱已驗收
資料不見／數字不同API網址、SQLite/PG、帳號、月份、帳本範圍回原資料庫與範圍，先比明細；不要直接重建資料庫
忘記密碼信未收到Brevo設定、已驗證寄件人與平台回應寄信是獨立整合；展示可用已知的自建展示帳號，勿假稱已寄出

信箱、背景、實際金額與匯率Email, backgrounds, manual entry and exchange

  1. 登入頁可申請信箱驗證。正式環境須真的收到驗證信；本機開發連結會明示沒有寄信。
  2. 展開登入背景，選三種預設或自己的照片。手機可選相簿／拍照，調整顯示方式、位置、亮度、模糊和遮罩；照片保存在此裝置。
  3. 點「手動輸入實際金額」直接填寫日期、金額、收支與分類，無需AI。
  4. 國際匯率可搜尋中英名稱、選不同幣別、查看來源與資料日期。目標TWD的結果可帶入手動記帳，再改成實際扣款後確認。
